# 코드 구조 설명 화면 — "가이드 투어형" 설계

## 배경

여행 앱 트리플(Triple)은 사용자가 목적지·기간만 정하면 AI가 동선과 일정을 짜주고, 최근에는 GPT를 연동해 짜여진 일정을 자연어로 요약·설명해주는 기능을 추가했다. 화면 구성은 지도(번호 핀 + 점선 동선) + Day1~4 탭 + 순서 리스트 카드 + AI 서사 박스로 이루어져 있다.

이 프로젝트(`프로젝트_방향성_및_계획.md`)의 목표인 "프로젝트마다 코드 구조를 시각적으로 설명해주는 앱"에 트리플의 이 패턴 — 구조화된 데이터를 공간 축(지도)과 시간 축(Day탭)으로 나눈 뒤 AI가 서사를 얹는 방식 — 을 적용한다.

## 컨셉

Day1~4 탭 자리에 이미 정리해둔 C4 줌 레벨(Context → Container → Component → Code)을 놓고, 지도의 동선 자리에 대상 프로젝트(RhythmTrainer)의 실제 핵심 플로우를 놓는다.

RhythmTrainer 기준 핵심 플로우 예시: 손목 흔들기(사용자 액션) → 워치에서 리듬 측정 → 폰으로 데이터 전송 → 화면에 결과 표시.

레벨을 넘어갈수록(Context → Code) 그래프의 언어가 비유에서 실제 파일/함수명으로, 노드 밀도가 최소에서 최대로 바뀐다. 이 진행이 이 설계의 핵심 축이다.

## 레벨별 콘텐츠 정의

| 레벨 | 그래프(동선)가 보여주는 것 | 언어 | 밀도 |
|---|---|---|---|
| Context | 사용자 행동 흐름 | 순수 비유, 파일명 없음 | 최소 — 핵심 노드만 (분기 없음) |
| Container | 앱/프레임워크 단위 (예: Watch App ↔ WatchConnectivity ↔ iOS App) | 비유 + 실제 이름 혼합 | 확장 — 구간 라벨, 분기 가능 |
| Component | 실제 클래스/레이어 (MotionService, PracticeViewModel, PracticeView 등) | 실제 이름 중심 | 가장 깊음 — 동시 분기 등 포함 |
| Code | 실제 함수 호출 순서 | 완전 기술적 | 순차적, 필요 시 비동기 분기만 |

**밀도 원칙**: Context는 항상 핵심만 남기고, 중간 두 레벨(Container/Component)에서 지도가 가장 붐빈다. Code는 다시 선형적으로 정리된다(호출 순서이므로).

## 탐색 원칙

### 계층 유지 (Nested Zoom, 평면 교체 아님)

더 깊은 레벨로 들어가도 상위 레벨에서 나뉜 갈래는 사라지지 않고, 그 갈래를 감싸는 그룹(스윔레인/컨테이너 박스)으로 화면에 계속 남는다. 레벨 전환은 "전체 그래프를 통째로 다른 해상도로 교체"하는 게 아니라 "상위 갈래 구조를 유지한 채 각 갈래 내부를 확대"하는 것이다.

예: Context에서 "🖐️ 손목 흔들기 → ⌚️ 시계에서 처리 → 📱 폰에서 처리 → ✅ 화면 표시"로 갈래가 2개(시계/폰)로 나뉘었다면, Container~Component로 깊어질 때도 "⌚️ 시계에서 처리" 그룹 박스 안에 `MotionService` 등이, "📱 폰에서 처리" 그룹 박스 안에 `WatchConnectivityService → PracticeViewModel → PracticeView`가 각각 중첩되어 표시된다. 두 그룹을 하나로 평평하게 섞지 않는다. Code 레벨까지 가도 이 중첩은 유지되어, 지금 보는 함수가 "시계 쪽"인지 "폰 쪽"인지 항상 그룹 라벨로 알 수 있다.

이는 실제 C4 모델의 관례와도 일치한다 — Component 다이어그램은 특정 Container "안에서" 그리는 것이지, 전체를 새로 평평하게 펼치는 게 아니다.

### 진입점은 항상 비유

사용자가 투어를 시작하는 순간(Context 레벨)은 항상 가장 쉬운 비유적 설명으로 시작한다. 기술 용어나 파일명을 먼저 노출하지 않는다.

### 시작–끝 범위를 먼저 보여줘 "미아 상태" 방지

가이드 투어형은 자유 탐색형과 달리 "지금 어디서부터 봐야 하지"라는 혼란이 없어야 한다. 핵심 플로우 순서를 기준으로, 투어 진입 시점에 전체 범위(시작 노드 ~ 끝 노드)를 먼저 한 번 보여준다 — 트리플의 헤더 "다낭, 3박4일 추천일정입니다"가 전체 범위를 한 줄로 미리 알려주는 것과 같은 역할이다. 이 헤더/개요는 레벨이 바뀌어도 유지되어, "지금 전체 중 어디를 보고 있고 어디까지 가면 끝인지"를 항상 알 수 있게 한다.

## 화면 구성 요소 (트리플 대응)

- **헤더**: 트리플의 "다낭, 3박4일 추천일정입니다" 자리 → "RhythmTrainer, Component 레벨입니다" 형태
- **지도**: 캔버스 위에 번호 핀 + 점선 경로 + 구간 라벨(SVG). 동시에 일어나는 흐름은 별도 색(회색 점선)의 분기로 표시
- **레벨 탭**: Context / Container / Component / Code, 트리플의 Day1~4 탭과 동일한 상호작용
- **순서 리스트 카드**: 지도 아래에 지도의 번호와 매칭되는 카드 목록
- **AI 서사 박스**: 카드 아래 문단형 설명, "AI가 분석한 설명입니다" 라벨로 출처 명시

## 리스트 정렬 규칙

파일 알파벳순, 의존성 위상정렬이 아니라 **핵심 플로우 순서**(사용자 액션 → 측정 → 전송 → 처리 → 표시)로 고정한다. 모든 레벨에서 동일한 원칙을 적용해, 탭을 넘겨도 "같은 여행의 다른 확대 수준을 보고 있다"는 일관성을 유지한다.

## AI 설명 생성 시점

프로젝트를 분석하는 시점에 레벨별로 1회 생성해 저장(캐싱)한다. 화면 진입/탭 전환 시 실시간으로 LLM을 호출하지 않는다. 이유: 화면 전환 속도, API 비용 예측 가능성.

## 범위

- 이번 설계는 RhythmTrainer 프로젝트 하나를 대상으로 한다.
- 다른 프로젝트(언어·프레임워크가 다른 경우 포함)로의 범용화는 `프로젝트_방향성_및_계획.md`의 5단계 과제이며 이 설계의 범위 밖이다.
- 그래프 자동 추출 알고리즘(AST 파싱, 어떤 관계를 노드/엣지로 잡을지의 세부 구현)은 이미 계획된 2단계 "도구 프로토타입 제작"의 범위이며, 이 문서는 그 결과를 어떤 화면 구조·톤으로 보여줄지에 집중한다.
